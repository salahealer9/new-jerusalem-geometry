# v0.5 NJG_MICHELL machine-readable geometry export schema

## Status

This document defines the machine-readable numerical geometry export for
Phase 5D of the v0.5 generative reconstruction.

The geometry export is distinct from the Phase 5C provenance manifest.

The two documents answer different questions:

```text
geometry export
    -> what is the numerical geometry of this object?

provenance manifest
    -> where does this object come from and how is its
       construction related to the evidence grammar?
````

The two representations are joined by stable `object_id`.

## Generative boundary

The geometry exporter consumes one already constructed:

```text
MichellComposite
```

It must not independently reconstruct the New Jerusalem geometry.

The exporter must not import or invoke:

```text
Figure 12 calibration geometry
Figure 14 calibration geometry
digitisation modules
registration modules
source-derived fitted geometry
alternative Moon-placement builders
alternative wall builders
Figure 14 aligned-anchor builders
build_michell_composite
```

The application-level generation script may call `build_michell_composite()`
and pass the resulting object to the exporter.

## Canonical architecture

```text
build_michell_composite(unit)
          |
          v
    MichellComposite
          |
          +--------------------+
          |                    |
          v                    v
 geometry export        provenance manifest
          |                    |
          +---------+----------+
                    |
                 object_id
```

The geometry exporter and provenance exporter are parallel downstream views of
the same supplied composite.

Neither is an input to the other.

## Canonical output

The canonical unit-one geometry export is planned at:

```text
data/geometry/njg_michell_v0_5/njg_michell_geometry.json
```

The project version remains `0.4.0` during v0.5 development.

## Schema identity

The top-level document should record:

```text
schema_name
schema_version
model_name
unit
coordinate_system
object_count
objects
```

Initial schema identifiers:

```text
schema_name    = njg_michell_geometry
schema_version = 1.0
model_name     = NJG_MICHELL
```

## Coordinate system

The canonical computational coordinate convention is:

```text
dimension       = 2
geometry        = Euclidean
origin          = [0.0, 0.0]
positive_x      = right
positive_y      = up
angle_origin    = positive x-axis
angle_direction = counter-clockwise
angle_units     = radians and degrees where applicable
```

These are model coordinates.

The SVG vertical reflection used for screen rendering is not part of the
geometry export.

## Numerical serialization

Canonical numerical values are exported from the supplied computational
objects without report-style rounding.

Python floating-point values are serialized using the deterministic
round-trip representation provided by the standard JSON serializer.

No coordinate should be rounded merely for presentation.

Where an angle is semantically important, both forms should be exported:

```text
angle_radians
angle_degrees
```

Radians remain the computational quantity.

Degrees are an audit convenience.

## Stable object identity

The geometry document must use the same 132 stable object identifiers already
established by Phase 5C.

The canonical object inventory is:

```text
  1  NJG_MICHELL composite root
  3  core geometric objects
 12  Moon circles
  1  polar-pivot wall polygon
 12  wall lines
 12  wall vertices
  7  Method-1 sevenfold points
 14  reciprocal-fourteenfold points
 28  four-triangle angular marks
 28  role-labelled scaffold points
  7  scaffold-derived heptagram vertices
  7  heptagram edges
---
132
```

The object-ID set in the geometry export and the object-ID set in the
provenance manifest must be identical.

The geometry exporter should not read the provenance JSON in order to create
these identifiers.

The correspondence is an independently tested cross-representation invariant.

## Canonical object record

Each geometry object should contain:

```text
object_id
geometry_type
geometry
attributes
```

`geometry_type` must use the same controlled geometric classification already
used in provenance:

```text
composite
circle
square
line
polygon
point
angular_mark
```

`geometry` contains numerical geometric data.

`attributes` contains non-coordinate computational metadata associated with
that object.

No historical evidence classification belongs in the geometry record.

## Composite root

Object:

```text
njg-michell-composite
```

Geometry type:

```text
composite
```

The root does not require independent coordinates.

Its geometry may contain structural summary values such as:

```text
unit
moon_count
wall_side_count
scaffold_point_count
heptagram_vertex_count
```

The composite root must not duplicate the complete child geometry.

## Core objects

```text
object_id      = earth-circle
```

### construction-circle

Uses the same circle representation.

### earth-square

```text
object_id      = earth-square

    centre:
        x
        y
```

The square is axis aligned by construction.

No rotated-square representation is introduced.

## Polar-pivot wall polygon

Object:

```text
polar-pivot-wall
```

Geometry type:

```text
polygon
```

Its geometry should contain:

```text
vertex_ids
side_ids
side_lengths
perimeter
mean_side_length

```

The polygon should reference the existing stable wall-vertex and wall-line
object identifiers.

The numerical perimeter, mean side length, area, and side lengths should be
read directly from `OuterWall`.

## Wall lines

The twelve wall-line objects retain their existing semantic names:

```text
wall_east
wall_east_north
wall_north_east
wall_north
wall_north_west
wall_west_north
wall_west
wall_west_south
wall_south_west
wall_south
wall_south_east
wall_east_south
```

Each is represented in the exact normal form already stored computationally:

```text
geometry_type = line

geometry:
    normal:
        x
        y
    offset
    tangency_point:
        x
        y
    side_start:
        x
        y
    side_end:
        x
        y
    side_length

attributes:
    wall_index
    moon_name
```

The infinite support line is described by:

```text
normal dot point = offset
```

`side_start` and `side_end` describe the finite polygon edge associated with
that support line.

They must be obtained from the existing `OuterWall.side_endpoints()` API.

The line itself must not be regenerated from the Moon geometry.

```text
    angle_degrees
```

## Four-triangle 28 angular marks

The independent four-triangle representation contains twenty-eight angular
marks:

```text
four-triangle-mark-00
...
four-triangle-mark-27
```

These objects are classified:

```text
geometry_type = angular_mark
```

Their canonical geometry is:

```text
angle_radians
angle_degrees
```

No Cartesian point should be synthesized for these records merely for export.

`MichellComposite` stores this representation as angular marks, not as an
independent point tuple.

The exporter must preserve that distinction.

The section should also record:

```text
four_triangle_scaffold_max_mismatch_radians
```

from the supplied composite.

## Heptagram vertices

The seven heptagram vertex records are:

```text
heptagram-vertex-00
...
heptagram-vertex-06
```

Each is:

```text
geometry_type = point

geometry:
    x
    y

attributes:
    heptagram_vertex_index
    scaffold_index
    source_scaffold_object_id
```

The source scaffold indices are exactly:

```text
7, 11, 15, 19, 23, 27, 3
```

The exporter may resolve these by exact equality against the supplied
`MichellComposite.scaffold.points`, as the Phase 5C provenance implementation
already verifies that every candidate vertex matches exactly one scaffold
point.

No source-plate coordinates may participate in this mapping.

## Heptagram edges

The seven edge objects are:

```text
heptagram-edge-00
...
heptagram-edge-06
```

Each is represented as:

```text
geometry_type = line

geometry:
    start:
        x
        y
    end:
        x
        y
    length

attributes:
    heptagram_edge_index
    start_vertex_index
    end_vertex_index
    start_vertex_object_id
    end_vertex_object_id
```

The edge ordering must come from:

```text
HeptagramGeometry.edge_index_pairs()
```

and lengths from:

```text
HeptagramGeometry.edge_lengths()
```

The current `{7/2}` traversal is therefore preserved without introducing a
second topology implementation.

## Section structure

The top-level JSON should make the geometry easy to inspect by both object ID
and construction layer.

A recommended structure is:

```text
schema_name
schema_version
model_name
unit
coordinate_system
object_count
sections
objects
```

with sections:

```text
core
moon_system
wall
sevenfold
fourteenfold
four_triangle_28
scaffold_28
heptagram
```

`sections` contain shared numerical metadata and ordered object-ID references.

`objects` contain the canonical 132 concrete object records.

This avoids duplicating complete geometric records inside every section.

## Object ordering

Canonical object serialization order is:

```text
composite root
core objects
Moon circles
wall polygon
wall lines
wall vertices
sevenfold points
fourteenfold points
four-triangle marks
scaffold points
heptagram vertices
heptagram edges
```

Within indexed families, ascending numerical index is used.

Moon and wall-line ordering follows the order already stored in the supplied
composite.

This order matches the Phase 5C provenance object inventory.

## Cross-representation invariants

Phase 5D tests must establish:

```text
geometry object IDs
    ==
provenance object IDs
```

and, for rendered objects:

```text
geometry object ID
    ==
provenance object ID
    ==
SVG data-provenance-id
```

The geometry exporter itself must not read either the provenance JSON or SVG
to produce its records.

The equality is tested externally.

## Geometry consistency invariants

The exported geometry must reproduce the supplied composite exactly within
normal floating-point serialization.

Tests should cover at least:

```text
core dimensions
12 Moon circles
12 wall lines
12 wall vertices
12 wall side lengths
wall perimeter
wall mean side length
wall area
7 sevenfold points and angles
14 fourteenfold points, angles, and gaps
28 four-triangle angular marks
28 scaffold points and roles
7 heptagram vertices
7 heptagram edges and lengths
```

## Determinism

For an identical `MichellComposite`, repeated geometry serialization must be
byte-identical.

Serialization should use deterministic JSON configuration:

```text
indent = 2
sort_keys = true
ensure_ascii = false
trailing newline = yes
```

## Scale behavior

The geometry exporter must preserve the supplied composite scale rather than
renormalize it internally.

Phase 5E will formally test the scaling laws:

```text
coordinates  -> linear in unit
lengths      -> linear in unit
areas        -> quadratic in unit
angles       -> invariant
topology     -> invariant
```

No scale-specific special case should therefore be built into the exporter.

## Evidence boundary

The geometry JSON does not contain:

```text
node_type
relation_type
evidence_status
source_status
historical claim text
```

Those belong to the provenance representation.

This separation is a required Phase 5D invariant.
