# v0.7 Phase 7B — frozen dodecagon vertex-radius audit protocol

## Status

Preregistered after the Phase 7A source clarification and before implementation
of any v0.7 vertex-radius audit code.

The original v0.7 protocol remains immutable.

## Source correction inherited from Phase 7A

The v0.7 preregistration initially treated the Figure 30 phrase "two radii to
the decagon" as referring to a separate ten-sided object.

Phase 7A established prospectively that Figure 30 instead depicts those radii
as radii to vertices of the already existing irregular twelve-sided wall.

Accordingly:

```text
historical literal term:
    decagon

v0.7 operational geometric interpretation:
    dodecagon vertex radii
```

The frozen v0.6 `DECAGON-*` record identifiers remain historical identifiers
and are not renamed inside v0.6 artifacts.

## Research question

Does the already frozen v0.5 `POLAR_PIVOT_WALL` contain exactly two
semantically defined vertex-radius classes, and how do those classes differ
from a regular dodecagon constructed from the same inherited apothem?

No new preferred wall geometry is to be invented in Phase 7B.

## Semantic vertex classes

Vertex classification is defined from wall-side incidence before radius values
are calculated.

For each wall vertex, inspect the two incident wall sides.

Define:

### `POLAR_ADJACENT_VERTEX`

A vertex for which at least one of the two incident wall sides is a polar side.

Expected count from the frozen wall topology:

```text
8
```

### `OBLIQUE_PAIR_VERTEX`

A vertex for which both incident wall sides are oblique sides.

Expected count from the frozen wall topology:

```text
4
```

The class labels must be assigned from side semantics, not from numerical
radius magnitude.

No clustering algorithm is permitted.

No radius threshold is permitted.

No historical dimensional value may influence class membership.

## Radius definition

For a wall vertex with normalized Cartesian coordinates `(x, y)`, define its
normalized centre radius as:

```text
r = sqrt(x^2 + y^2)
```

The common origin is the inherited centre of the New Jerusalem construction.

For each semantic class report:

- vertex count;
- ordered vertex IDs;
- individual normalized radii;
- minimum radius;
- maximum radius;
- mean radius;
- within-class spread.

A class may be declared numerically degenerate only if its within-class spread
is at or below the preregistered numerical tolerance.

## Numerical tolerance

The Phase 7B geometric equality tolerance is:

```text
absolute tolerance = 1e-12 normalized units
relative tolerance = 1e-12
```

This tolerance is for floating-point identity/equality checks only.

It is not a historical-fit tolerance and must never be compared with the
Figure 30 working tolerance.

## Regular dodecagon baseline

The original v0.7 preregistration used the historical label:

```text
REGULAR_DECAGON_BASELINE
```

because the source typo had not yet been resolved.

Following Phase 7A, the operational v0.7 name is:

```text
REGULAR_DODECAGON_BASELINE
```

This is a prospective terminology correction, not a new candidate introduced
after seeing dimensional residuals.

The regular baseline must use:

```text
centre:
    inherited origin

side count:
    12

polar-side apothem:
    inherited normalized apothem 8.5

side outward-normal angles:
    k * 30 degrees, k = 0,...,11
```

The baseline therefore has no fitted geometric parameter.

Its circumradius is derived geometrically from its apothem:

```text
R_regular = 8.5 / cos(15 degrees)
```

The implementation should derive this value rather than hard-code a decimal
circumradius.

## Comparison quantities

Phase 7B may calculate only normalized geometric quantities.

Required comparisons are:

1. regular-baseline vertex radius;
2. mean `POLAR_ADJACENT_VERTEX` radius;
3. mean `OBLIQUE_PAIR_VERTEX` radius;
4. difference between each frozen-wall class and the regular baseline;
5. ratio of the two frozen-wall radius classes;
6. radial displacement of every frozen-wall vertex from its corresponding
   regular-baseline vertex;
7. maximum absolute radial displacement;
8. classwise equality/spread checks.

The raw geometric ratio of the two frozen classes may be calculated.

It must not be compared with the exposed historical ratio in Phase 7B.

## Correspondence to the regular baseline

The regular baseline and frozen wall share the same centre and cardinal
orientation.

Vertex correspondence must be determined by cyclic geometric order around the
origin and inherited wall semantics.

It must not be chosen by minimizing distance to the historical dimensional
targets.

If the repository's semantic wall IDs permit an exact inherited
correspondence, that correspondence must be preferred over any numerical
nearest-neighbour assignment.

## Construction-level hypothesis

The polar-pivot construction was defined by retaining the regular polar sides
and pivoting the neighboring oblique sides at the relevant polar endpoints.

Phase 7B therefore tests the following construction-level consequence:

```text
the eight POLAR_ADJACENT_VERTEX positions coincide with regular-dodecagon
vertex positions to floating-point tolerance;

the four OBLIQUE_PAIR_VERTEX positions are displaced inward relative to the
regular-dodecagon baseline.
```

This hypothesis is geometric and follows from the already frozen construction
rule.

It is not inferred from the Figure 30 dimensional targets.

## Implementation boundary

The Phase 7B implementation may import or consume:

- Python standard library;
- frozen v0.5 geometry/building modules needed to expose wall semantics;
- the frozen v0.5 machine-readable geometry artifact;
- deterministic SVG utilities already present in the repository.

It must not import or consume:

- `historical_residuals`;
- the v0.6 metrology registry;
- Phase 6E comparison artifacts;
- historical dimensional target tables;
- code whose purpose is to optimize against historical dimensions.

Any unavoidable import dependency that indirectly loads those targets must be
reported before Phase 7B is frozen.

## Leakage audit

Before Phase 7B is committed as complete, the implementation source and
geometry-only SVG generators must be scanned for the exposed target literals.

The scan must distinguish documentation/provenance text from executable
geometry code.

The geometry implementation must report:

```text
historical_targets_loaded = false
historical_comparison_metrics_calculated = false
```

## Deterministic regeneration

The JSON and both Phase 7B SVGs must regenerate byte-identically.

Absolute machine paths must not appear in generated artifacts.

## Stopping rule

Phase 7B terminates with one of:

```text
TWO_SEMANTIC_RADIUS_CLASSES_CONFIRMED
SEMANTIC_CLASSES_NOT_RADIUS_DEGENERATE
FROZEN_WALL_TOPOLOGY_MISMATCH
REGULAR_BASELINE_CORRESPONDENCE_UNRESOLVED
IMPLEMENTATION_BOUNDARY_VIOLATION
```

A failure is not grounds for changing the wall geometry or consulting the
historical dimensional targets.

necessary.

new geometric-construction phase.
