# v0.5 NJG_MICHELL provenance-manifest schema

## Status

This document defines the machine-readable provenance architecture for
Phase 5C of the v0.5 generative reconstruction.

The provenance layer does not create a new historical or evidential
classification system.

It reuses the existing construction grammar:

```text
docs/specification/construction_nodes.csv
docs/specification/construction_dependencies.csv
````

and geometric claim matrix:

```text
docs/sources/geometric_claim_matrix.csv
```

## Principle

Geometric-object identity and evidential status are deliberately separated.

A rendered or exported object may belong to one or more construction-grammar
nodes.

The object itself does not receive an independent `evidence_status`.

Evidence status belongs to construction dependencies in the existing grammar.

For example:

```text
moon-q1-a
    |
    +-- NJG_INC_MOONS
    |
    +-- MOON_GROUPS_4X3
```

while the grammar separately records:

```text
NJG_INC_MOONS
    -- groups_as / stated_exact -->
MOON_GROUPS_4X3
```

Likewise:

```text
polar-pivot-wall
    |
    +-- POLAR_PIVOT_WALL
```

does not itself acquire the label `project_inference`.

Instead the grammar preserves:

```text
REGULAR_DODECAGON_BASELINE
    -- constructs_from / project_inference -->
POLAR_PIVOT_WALL

NJG_INC_MOONS
    -- tangent_constraint / project_inference -->
POLAR_PIVOT_WALL
```

This distinction prevents object-level provenance from overstating the
historical evidence.

## Canonical object record

Each concrete generative object is represented by a record with the following
logical fields:

```text
object_id
geometry_type
grammar_nodes
role
source_object_ids
rendered_svg_id
attributes
```

### object_id

A stable identifier for one computational object.

Where a corresponding SVG object already has a stable ID, the provenance
object should use the same identifier where practical.

Examples:

```text
earth-circle
earth-square
construction-circle
moon-q1-a
polar-pivot-wall
wall_east
scaffold-point-07
heptagram-vertex-00
heptagram-edge-00
```

### geometry_type

A structural geometric classification.

Initial controlled values are expected to include:

```text
composite
circle
square
line
polygon
point
angular_mark
```

This is a geometric/software classification, not an evidence classification.

### grammar_nodes

One or more existing construction-grammar node identifiers associated with the
object.

Examples:

```text
earth-circle
    -> EARTH_CIRCLE
```

```text
moon-east
    -> CARDINAL_MOONS
    -> NJG_INC_MOONS
    -> MOON_GROUPS_4X3
```

```text
moon-q1-a
    -> NJG_INC_MOONS
    -> MOON_GROUPS_4X3
```

```text
polar-pivot-wall
    -> POLAR_PIVOT_WALL
```

```text
scaffold-point-07
    -> SCAFFOLD_28
```

```text
heptagram-vertex-00
    -> FIG14_SCAFFOLD_VERTICES
```

```text
heptagram-edge-00
    -> FIG14_HEPTAGRAM_7_2
```

All referenced node identifiers must already exist in
`construction_nodes.csv`.

The provenance exporter must not invent alternative grammar-node identifiers.

### role

An optional semantic role within a larger construction.

Examples include:

```text
cardinal_moon
oblique_moon
moon_centre
inter_moon_gap
intersection_positioner
wall_line
wall_vertex
heptagram_vertex
heptagram_edge
```

The role is descriptive and does not itself carry historical evidence.

### source_object_ids

Optional stable object identifiers from which a downstream object is directly
selected or assembled.

For example, a scaffold-derived heptagram vertex may record the corresponding
scaffold point:

```text
heptagram-vertex-00
    source_object_ids:
        scaffold-point-07
```

A heptagram edge may record its two endpoint objects:

```text
heptagram-edge-00
    source_object_ids:
        heptagram-vertex-00
        heptagram-vertex-02
```

Object-level source references describe computational provenance only.

They do not replace or modify the construction dependency grammar.

### rendered_svg_id

The stable SVG identifier of the corresponding rendered object, where one
exists.

Some computational objects are intentionally not shown in the final
composite SVG and therefore have no `rendered_svg_id`.

Examples of non-rendered intermediate objects may include:

```text
Method-1 sevenfold points
reciprocal fourteenfold points
independent four-triangle angular marks
individual wall support lines
```

Their absence from the SVG does not remove them from computational provenance.

### attributes

A deterministic mapping of object-specific descriptive metadata.

Examples may include:

```text
scaffold_index
scaffold_role
moon_name
moon_group
moon_group_role
wall_index
wall_moon_name
heptagram_vertex_index
heptagram_start_index
heptagram_end_index
```

Attributes must not be used to introduce a parallel evidence vocabulary.

## Canonical v0.5 object inventory

The provenance layer should cover the canonical `MichellComposite`, including
where practical:

```text
NJG_MICHELL composite root
Earth circle
Earth square
construction circle
12 Moon circles
polar-pivot wall polygon
12 wall lines
12 wall vertices
7 Method-1 sevenfold points
14 reciprocal-fourteenfold points
28 independently generated four-triangle angular marks
28 role-labelled scaffold points
7 scaffold-derived heptagram vertices
7 heptagram edges
```

This is broader than the visible SVG.

The provenance manifest therefore describes the generative computational
object, not merely the rendered picture.

## Figure 14 boundary

The current scaffold-derived Figure 14 vertices belong to:

```text
FIG14_SCAFFOLD_VERTICES
```

The star-edge topology belongs to:

```text
FIG14_HEPTAGRAM_7_2
```

The grammar must continue to preserve the distinction:

```text
SCAFFOLD_28
    -- selects / implementation_only -->
FIG14_SCAFFOLD_VERTICES

FIG14_SCAFFOLD_VERTICES
    -- candidate_correspondence / hypothesis_to_test -->
FIG14_HEPTAGRAM_7_2
```

The provenance manifest must not convert that relationship into an established
historical dependency.

## Grammar snapshot

The exported provenance document should contain a machine-readable snapshot of
the construction-grammar records needed to interpret its object references.

The source CSV files remain authoritative.

The JSON snapshot is a deterministic representation for audit and portability,
not a replacement source of truth.

The manifest should record SHA-256 hashes of:

```text
docs/specification/construction_nodes.csv
docs/specification/construction_dependencies.csv
docs/sources/geometric_claim_matrix.csv
```

This binds each generated provenance document to the exact grammar and claim
matrix from which it was produced.

## Claims

Claim identifiers are not copied manually onto individual geometric objects
where doing so would duplicate the grammar.

Instead:

```text
object
    -> grammar node
    -> node and dependency claim_ids
    -> geometric claim matrix
```

is the preferred provenance path.

This makes the existing claim matrix the authoritative claim catalogue.

## SVG correspondence

Phase 5B already provides stable SVG identifiers and semantic attributes.

Phase 5C may add:

```text
data-provenance-id
```

to rendered objects so that SVG elements can be joined directly to provenance
records.

Where possible:

```text
data-provenance-id == object_id == rendered_svg_id
```

No geometry may change as a consequence of adding provenance metadata.

## Determinism

For an identical:

```text
MichellComposite
construction_nodes.csv
construction_dependencies.csv
geometric_claim_matrix.csv
```

the serialized provenance JSON must be byte-identical.

Object ordering must therefore be explicit and deterministic.

JSON key ordering and numeric serialization must also be deterministic.

## Generative boundary

The provenance builder may inspect the supplied `MichellComposite`.

It must not rebuild the geometry.

It must not import:

```text
Figure 12 calibration geometry
Figure 14 calibration geometry
digitisation modules
registration modules
source-derived fitted geometry
Figure 14 aligned-anchor builders
alternative Moon builders
alternative wall builders
```

The provenance layer describes an existing composite; it does not generate a
new one.

## Evidence boundary

The following concepts remain distinct:

```text
geometry_type
node_type
relation_type
evidence_status
source_status
```

They must not be collapsed into one generic provenance label.

Specifically:

* `geometry_type` describes a computational geometric object;
* `node_type` describes a construction-grammar node;
* `relation_type` describes a dependency operation;
* `evidence_status` describes support for a dependency edge;
* `source_status` describes the status of a claim in the claim matrix.

This separation is a required invariant of Phase 5C.

The canonical unit-one provenance export is expected at:

```text

```
